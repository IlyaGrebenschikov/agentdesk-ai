# DayWave — Product & MVP Roadmap

> Рабочая документация продукта и план реализации по этапам. Документ описывает целевую веб-платформу персонального AI-ассистента, а не только текущий демонстрационный фронтенд.

## 1. Видение продукта

**DayWave** — веб-приложение персонального AI-ассистента, который получает контекст из подключённых сервисов пользователя, помогает планировать день, искать и обобщать информацию, выполнять согласованные действия и запускать автоматизации по расписанию.

Веб-приложение — основной интерфейс и центр управления. Telegram — дополнительный канал уведомлений и быстрых команд, а не основа продукта.

### Принципы продукта

1. **Web-first:** все основные сценарии доступны из браузера.
2. **Интеграции как инструменты:** календарь, почта, заметки и мессенджеры подключаются независимо.
3. **Контроль пользователя:** перед внешними или потенциально опасными действиями ассистент запрашивает подтверждение.
4. **Прозрачность:** пользователь видит, какие источники использовались, какие инструменты вызывались и чем завершилось выполнение.
5. **Надёжное выполнение:** длительные задачи и автоматизации выполняются асинхронно, с логированием, повторами и защитой от дублирования.
6. **Постепенное усложнение AI:** начинать с одного управляемого агента и небольшого набора инструментов, а не строить мультиагентную платформу.

## 2. Целевая аудитория и ключевые сценарии

Первая версия ориентирована на одного пользователя, который хочет свести повседневные рабочие процессы в одно место.

Основные сценарии:

- Утром получить краткую сводку дня: встречи, важные письма и задачи.
- Спросить ассистента о расписании или содержимом подключённых источников.
- Найти свободное время и предложить слот для встречи.
- Получить уведомление в Telegram о важном событии или результате автоматизации.
- Запустить повторяющийся workflow, например ежедневный дайджест.
- Посмотреть историю действий ассистента и понять, откуда взялся результат.

## 3. Границы MVP

### В MVP входит

- Регистрация, вход, выход и управление сессией.
- Веб-дашборд.
- Чат с AI-ассистентом.
- Один LLM-провайдер через абстракцию.
- Один агент с ограниченным циклом tool calling.
- Подключение Google Calendar по OAuth.
- Чтение календарных событий и ответы на вопросы о расписании.
- Подключение Telegram как канала доставки уведомлений.
- Простые автоматизации по расписанию.
- История диалогов, запусков автоматизаций и вызовов инструментов.
- Подтверждение перед действиями, изменяющими внешние данные.

### Не входит в первый MVP

- Визуальный конструктор агентов и графов.
- Полноценная мультиагентная система.
- Свободное выполнение произвольного кода.
- Доступ ко всем сервисам Google.
- Полноценная почтовая интеграция и отправка писем.
- RAG по произвольным файлам, векторная база и сложный ingestion.
- Голосовой интерфейс и realtime voice.
- Мобильное приложение.
- Маркетплейс интеграций.
- Платежи, тарифы и командные workspace.
- Самостоятельное выполнение критичных действий без подтверждения.

**Критерий хорошего MVP:** пользователь может подключить календарь, спросить ассистента о своём дне, получить полезный ответ с опорой на реальные события и получать ежедневную сводку в Telegram.

## 4. Этапы разработки

Оценки ниже — ориентир для одного разработчика с опытом Python backend. Они не включают длительное исследование неизвестных API и согласование OAuth-приложений.

### Этап 0. Подготовка проекта и технический фундамент

**Цель:** превратить текущий статический интерфейс в основу приложения, которую можно безопасно расширять.

Задачи:
- Зафиксировать продуктовые сценарии и границы MVP.
- Определить структуру frontend и backend репозиториев.
- Настроить конфигурацию через environment variables.
- Добавить Docker Compose для локальной разработки.
- Поднять PostgreSQL и миграции.
- Настроить форматирование, lint, type checking и тесты.
- Добавить `/health/live` и `/health/ready`.
- Описать API-контракт и единый формат ошибок.
- Ввести логирование с request/correlation ID.

Результат:
- Приложение запускается одной документированной командой.
- Есть базовая CI-проверка.
- Frontend и backend могут развиваться независимо.

Готово, когда:
- Чистый checkout запускается по инструкции.
- Миграции применяются с нуля.
- CI выполняет lint и тесты.
- Секреты не хранятся в репозитории.

### Этап 1. Пользователи, регистрация и авторизация

**Цель:** обеспечить персональные аккаунты и изоляцию данных.

Функциональность:
- Регистрация по email и паролю.
- Вход и выход.
- Хеширование паролей современным алгоритмом.
- Access/refresh token или серверная cookie-сессия.
- Обновление и отзыв сессии.
- Получение и изменение профиля.
- Защита всех приватных API.
- Ограничение частоты попыток входа и регистрации.
- Восстановление пароля можно вынести в следующий релиз, если MVP закрытый.

Сущности:
- `User`
- `Session` или `RefreshToken`
- `UserSettings`

API (пример):
- `POST /api/v1/auth/register`
- `POST /api/v1/auth/login`
- `POST /api/v1/auth/refresh`
- `POST /api/v1/auth/logout`
- `GET /api/v1/users/me`
- `PATCH /api/v1/users/me`

Готово, когда:
- Пользователь может зарегистрироваться и войти.
- Сессия переживает перезагрузку страницы.
- Пользователь A не может получить данные пользователя B.
- Logout отзывает refresh token/сессию.

### Этап 2. Подключение Google Calendar

**Цель:** дать ассистенту первый реальный источник контекста.

Функциональность:
- OAuth 2.0 Authorization Code flow.
- Минимально необходимые scopes.
- Безопасное хранение refresh token в зашифрованном виде.
- Просмотр подключённых интеграций.
- Отключение интеграции и отзыв токенов.
- Получение списка событий за период.
- Нормализация событий во внутренний DTO.
- Обработка истёкших и отозванных токенов.
- Синхронизация по запросу; периодическую синхронизацию добавить после проверки базового сценария.

Сущности:
- `IntegrationConnection`
- `CalendarEvent` (при необходимости локального кеша)
- `OAuthState` (может быть временным хранилищем)

Важные ограничения:
- Не запрашивать полный доступ к Google-аккаунту, если достаточно Calendar scopes.
- Проверять OAuth `state`.
- Не отдавать токены во frontend.
- Учитывать timezone и события на весь день.
- Не считать отсутствие событий доказательством отсутствия доступа: отдельно обрабатывать ошибки интеграции.

Готово, когда:
- Пользователь подключает Google Calendar.
- В интерфейсе виден статус подключения.
- Backend может получить события текущего дня.
- Пользователь может отключить интеграцию.
- Секреты OAuth не попадают в логи и ответы API.

### Этап 3. AI-чат и первый агент с инструментами

**Цель:** реализовать полезный диалог, который использует реальные данные календаря.

Функциональность:
- Интерфейс диалогов и сообщений.
- Создание и получение диалогов.
- Хранение истории сообщений.
- Streaming-ответы, если это поддерживает выбранный провайдер.
- Абстракция LLM-провайдера.
- Системные инструкции и ограничение контекста.
- Tool calling для чтения календаря.
- Ограничение количества tool calls и общего времени выполнения.
- Сохранение трассы выполнения: модель, инструменты, статусы, ошибки и длительность.
- Понятные ответы при недоступности провайдера или интеграции.

Первый набор инструментов:
- `get_calendar_events(start, end)`
- `get_free_slots(start, end, duration_minutes)`
- `get_current_datetime(timezone)`

Не добавлять сразу универсальный инструмент `execute_anything`. Каждый tool должен иметь конкретную схему входных данных, проверку прав и понятный результат.

Сущности:
- `Conversation`
- `Message`
- `AgentRun`
- `ToolCall`

Пример цикла:
1. Backend получает сообщение пользователя.
2. Загружает ограниченный контекст диалога.
3. Передаёт запрос модели с доступными tools.
4. Валидирует запрос инструмента.
5. Проверяет пользователя и доступность интеграции.
6. Выполняет tool.
7. Передаёт результат модели.
8. Возвращает ответ и сохраняет trace.

Готово, когда:
- Пользователь спрашивает «Что у меня сегодня?» и получает ответ по реальным событиям календаря.
- История диалога сохраняется.
- Ошибки tool call видны в trace.
- Агент не может вызвать инструмент, недоступный этому пользователю.
- Цикл агента ограничен по числу итераций и времени.

### Этап 4. Telegram как дополнительный канал

**Цель:** доставлять уведомления из DayWave в Telegram, сохраняя веб-приложение главным интерфейсом.

Функциональность:
- Экран подключения Telegram.
- Привязка Telegram-аккаунта через одноразовый код или deep link.
- Проверка владения чатом.
- Хранение Telegram chat ID.
- Отправка тестового уведомления.
- Настройки типов уведомлений.
- Отключение Telegram.
- Обработка блокировки бота и ошибок доставки.

Сценарии:
- Ежедневная сводка.
- Напоминание о ближайшей встрече.
- Результат завершённой автоматизации.
- Уведомление, что ассистенту требуется подтверждение.

Важно:
- Telegram не является источником истины для аккаунта.
- Все настройки и история доступны в веб-приложении.
- Бот не должен принимать команды, обходящие авторизацию и права backend.

Готово, когда:
- Пользователь связывает Telegram с аккаунтом DayWave.
- Может отправить тестовое уведомление.
- Уведомления отправляются только в привязанный чат.
- Пользователь может отключить канал.

### Этап 5. Автоматизации и фоновые задачи

**Цель:** выполнять полезные сценарии без открытой вкладки браузера.

Первый workflow:
**Daily briefing**
1. Запускается по расписанию пользователя.
2. Получает события календаря на день.
3. Формирует краткую сводку через LLM.
4. Сохраняет результат.
5. Отправляет его в Telegram.
6. Показывает результат в Dashboard.

Функциональность:
- Создание, просмотр, включение и выключение автоматизации.
- Расписание и timezone пользователя.
- Фоновая очередь задач.
- Статусы `pending`, `running`, `succeeded`, `failed`, `cancelled`.
- Повторные попытки с backoff для временных ошибок.
- Идемпотентность запуска.
- Логи и история запусков.
- Ограничение частоты и стоимости AI-запросов.

Сущности:
- `Automation`
- `AutomationRun`
- `ScheduledJob` (если требуется отдельная модель расписания)

Технические рекомендации:
- Не выполнять расписание внутри процесса FastAPI через локальные таймеры.
- Использовать отдельный worker и scheduler.
- Redis может выступать брокером/хранилищем очереди, PostgreSQL — источником истины для бизнес-состояния.
- Уникальный ключ запуска должен предотвращать повторную отправку одного дайджеста.
- Учитывать переходы летнего/зимнего времени.

Готово, когда:
- Daily briefing запускается по расписанию без открытого браузера.
- Результат доступен в истории.
- Повторная доставка не создаёт дубликат.
- Ошибочный запуск можно диагностировать.

### Этап 6. Безопасное выполнение действий и подтверждения

**Цель:** перейти от чтения контекста к ограниченным действиям от имени пользователя.

Примеры:
- Создать событие в календаре.
- Изменить время встречи.
- Подготовить черновик письма (без отправки).

Обязательный flow:
1. Агент формирует структурированное предложение действия.
2. Backend проверяет схему, права и ограничения.
3. Пользователь видит понятное описание действия.
4. Пользователь подтверждает или отклоняет его.
5. Backend повторно проверяет актуальность данных.
6. Выполняет действие с idempotency key.
7. Сохраняет результат и аудит.

Не разрешать модели самостоятельно подтверждать собственные действия. Подтверждение должно быть отдельным пользовательским действием, привязанным к конкретному предложению и сроку его действия.

Сущности:
- `PendingAction`
- `ActionExecution`
- `AuditLog`

Готово, когда:
- Внешнее изменение невозможно без валидного подтверждения.
- Повторный запрос подтверждения не выполняет действие дважды.
- Пользователь видит результат и историю выполнения.

### Этап 7. Расширение продукта

После проверки основного сценария можно добавлять:
- Gmail: чтение писем, дайджест, черновики.
- Notion: поиск страниц и извлечение контекста.
- Поиск в интернете с цитированием источников.
- Задачи и персональная база знаний.
- RAG по документам.
- Дополнительные модели и fallback-провайдеры.
- Более гибкие триггеры автоматизаций.
- Голосовой интерфейс.
- Конструктор workflow, если появится реальная потребность.

Мультиагентность и визуальный конструктор не являются обязательной целью. Сначала нужно доказать ценность одного агента с надёжными инструментами.

## 5. Предлагаемая архитектура backend

Для текущего опыта и масштаба проекта подходит **модульный монолит на FastAPI** с вертикальными срезами/CQRS и явными границами слоёв.

```text
backend/
  src/
    app/
      main.py
      config/
      bootstrap/
    modules/
      identity/
        domain/
        application/
        infrastructure/
        presentation/
      integrations/
        domain/
        application/
        infrastructure/
        presentation/
      conversations/
        domain/
        application/
        infrastructure/
        presentation/
      agent/
        domain/
        application/
        infrastructure/
        presentation/
      automations/
        domain/
        application/
        infrastructure/
        presentation/
      notifications/
        domain/
        application/
        infrastructure/
        presentation/
    shared/
      application/
      infrastructure/
  workers/
  migrations/
  tests/
```

### Ответственность слоёв

- `domain`: простые сущности, value objects и правила, не зависящие от инфраструктуры.
- `application`: use cases/handlers, DTO, порты и orchestration.
- `infrastructure`: SQLAlchemy, внешние SDK, LLM-клиенты, очереди, OAuth-хранилище.
- `presentation`: FastAPI routers, Pydantic-схемы, преобразование HTTP DTO в application DTO.
- `workers`: точки входа фоновых задач; бизнес-сценарии вызываются через application layer.

Не передавать Pydantic-схемы и ORM-модели в application handlers. Внешние провайдеры и репозитории подключать через интерфейсы/порты.

### Основные модули

| Модуль | Ответственность |
|---|---|
| identity | Пользователи, пароли, сессии |
| integrations | OAuth, подключения, токены, адаптеры сервисов |
| conversations | Диалоги и сообщения |
| agent | LLM orchestration, tool registry, agent runs |
| automations | Правила, расписания, запуски |
| notifications | Telegram и другие каналы доставки |
| audit | История значимых действий и диагностика |

`audit` можно сначала реализовать как часть соответствующих модулей, выделяя отдельно только при росте.

## 6. Предлагаемый стек

### Frontend
- Vue 3 Composition API
- Vite
- Vue Router
- TypeScript (желательно добавить до активного роста проекта)
- Pinia для общего состояния, когда оно действительно появится
- TanStack Query for Vue или собственный тонкий API layer для серверного состояния
- Zod или runtime-валидация на границе, если потребуется

### Backend
- Python 3.12+
- FastAPI
- Pydantic v2
- SQLAlchemy 2.x async
- PostgreSQL
- Alembic
- Redis
- Taskiq/Celery/ARQ — выбрать один инструмент фоновых задач, не смешивать несколько без необходимости
- httpx
- pytest

### AI
- Один провайдер LLM на старте через собственный интерфейс.
- Structured outputs и tool/function calling.
- LangGraph или другой orchestration framework подключать только если простой управляемый цикл перестанет покрывать сценарии.
- LangChain не обязателен: не нужно добавлять framework только ради самого факта его использования.

### Инфраструктура
- Docker Compose для локальной разработки.
- GitHub Actions.
- Структурированные логи.
- Sentry или аналог для ошибок на более позднем этапе.
- Метрики стоимости, latency и количества tool calls.

## 7. Frontend: целевые модули

Текущий демонстрационный frontend содержит основные экраны, но его следует постепенно привести к feature-oriented структуре.

```text
src/
  app/
    router/
    providers/
    layouts/
  pages/
    dashboard/
    auth/
    assistant/
    calendar/
    integrations/
    automations/
    settings/
  features/
    sign-in/
    connect-integration/
    send-message/
    create-automation/
    approve-action/
  entities/
    user/
    conversation/
    integration/
    automation/
    calendar-event/
  shared/
    api/
    ui/
    composables/
    lib/
    types/
```

Правила:
- Страница композирует features и widgets, а не содержит всю бизнес-логику.
- API-запросы находятся в `shared/api` или рядом с соответствующей entity/feature.
- Компоненты не обращаются напрямую к `localStorage` для бизнес-состояния.
- Формы валидируются на клиенте для UX, но backend всегда повторяет проверки.
- Состояние сервера не дублируется без причины в Pinia.
- Для загрузки, пустых состояний, ошибок и повторных запросов есть отдельные UI-состояния.

## 8. Черновая модель данных

Минимальный набор таблиц, который будет уточняться по мере реализации:

- `users`: id, email, password_hash, created_at.
- `sessions`: id, user_id, refresh_token_hash, expires_at, revoked_at.
- `user_settings`: user_id, timezone, locale, notification_preferences.
- `integration_connections`: id, user_id, provider, external_account_id, encrypted_credentials, status, created_at.

## 9. Нефункциональные требования

### Безопасность
- OAuth credentials и refresh tokens шифруются на backend.
- Секреты и токены не попадают в логи.
- Все запросы к пользовательским данным проверяют ownership.
- Tools имеют allowlist и строгие схемы.
- Для изменяющих действий требуется подтверждение.
- Есть rate limiting для auth, chat и дорогих операций.
- CORS, cookies и CSRF настраиваются под выбранную схему авторизации.
- LLM prompt не считается доверенной границей безопасности: результаты внешних документов могут содержать prompt injection.

### Надёжность
- Внешние HTTP-запросы имеют timeout.
- Для временных ошибок предусмотрены retries с backoff.
- Повторные запуски и доставки идемпотентны.
- Длительные операции не удерживают HTTP-запрос открытым.
- Ошибки интеграций отделены от ошибок самого приложения.
- Есть health checks, логи и трассировка agent runs.

### AI-качество и стоимость
- Логировать модель, latency, токены и стоимость там, где провайдер это предоставляет.
- Ограничивать размер истории и контекста.
- Ограничивать число tool calls на один run.
- Иметь timeout и максимальный бюджет одного запуска.
- Проверять ответы на наборе реалистичных сценариев.
- Не отправлять модели больше персональных данных, чем нужно для конкретной задачи.

## 10. Тестирование

Минимальная стратегия:

- Unit tests: use cases, правила, tool input validation.
- Integration tests: repositories, PostgreSQL, очередь, OAuth callback.
- Contract tests: адаптеры внешних сервисов и LLM provider.
- API tests: auth, ownership, ошибки, pagination.
- Agent evals: набор вопросов и ожидаемых действий на заранее подготовленных данных.
- E2E: регистрация → подключение календаря → вопрос ассистенту → получение ответа.
- Automation E2E: создание расписания → запуск worker → сохранение результата → Telegram delivery.

Для AI-тестов не полагаться только на точное совпадение текста. Проверять корректность выбранного инструмента, аргументов, фактов и итогового поведения.

## 12. Definition of Done для каждой фичи

Фича считается готовой, когда:
- Есть понятный пользовательский сценарий и критерии приёмки.
- Реализованы happy path и основные ошибки.
- Проверены права доступа и изоляция пользователей.
- Добавлены тесты на бизнес-логику.
- Добавлены логи, достаточные для диагностики.
- UI показывает loading, empty, success и error состояния.
- Документация и API-контракт обновлены.
- Секреты и персональные данные обрабатываются безопасно.

## 13. Что делать первым

Не начинай с «умного Джарвиса», который умеет всё. Последовательность должна быть такой:

1. Довести текущий frontend до аккуратной компонентной структуры.
2. Поднять backend и авторизацию.
3. Реализовать Google Calendar OAuth и чтение событий.
4. Сделать чат, который умеет только отвечать на вопросы по календарю.
5. Добавить Telegram как канал уведомлений.
6. Реализовать ежедневную сводку через scheduler и worker.
7. Добавить подтверждаемые действия.

Так получится законченный вертикальный продукт на каждом этапе: сначала пользовательские аккаунты, затем реальные данные, затем AI, затем уведомления и автоматизация. Это существенно полезнее, чем одновременно строить конструктор агентов, RAG, десяток интеграций и сложную мультиагентную архитектуру.
