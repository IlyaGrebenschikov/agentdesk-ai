# AgentDesk — low-code конструктор AI-workflow с упором на отладку

**Версия:** 0.3  
**Статус:** проектная спецификация  
**Цель:** учебный, но похожий на production backend-проект для портфолио Python Backend-разработчика

---

## 1. Идея продукта

AgentDesk — low-code платформа для сборки и запуска AI-workflow. Пользователь собирает схему из визуальных узлов, соединяет их, настраивает модели и инструменты, проверяет граф и запускает workflow без необходимости писать glue-код.

**Главное отличие AgentDesk — отладка как основная функция продукта, а не экран с общим статусом запуска.** Визуальная схема должна показывать, что именно произошло во время конкретного запуска: какие узлы выполнились, какие данные получили и вернули, сколько заняли времени и денег, где возникла ошибка и можно ли безопасно повторить шаг.

Продукт ориентирован на проблему, знакомую разработчикам визуальных LLM-конструкторов: когда workflow падает, одного статуса `Failed` недостаточно. Разработчику нужен воспроизводимый след исполнения, понятная причина отказа и удобный путь от ошибки к исправлению. Для снижения объёма самописного runtime AgentDesk использует **LangGraph как движок исполнения графов**, а интеграции моделей и некоторые стандартные абстракции получает через **LangChain**. При этом собственные модели `Execution`, `NodeRun` и `TraceEvent`, API и Debugger остаются независимыми от этих библиотек.

### Основной сценарий

Пользователь собирает workflow `Error Analyst`:

1. `Input` принимает период и сервис, который нужно исследовать.
2. `AI Agent` анализирует задачу и при необходимости вызывает разрешённые инструменты.
3. `Search Logs` ищет совпадения в демо-логах.
4. `Condition` выбирает ветку в зависимости от найденных ошибок.
5. `LLM` формирует объяснение и рекомендации.
6. `Output` возвращает итоговый отчёт.

После запуска пользователь видит ту же схему, но поверх узлов отображается фактическое исполнение. У каждого узла доступны входные и выходные данные, длительность, статус, попытки, ошибки, вызовы LLM, usage и оценочная стоимость. При падении UI выделяет конкретный узел и показывает диагностическую информацию.

Для MVP используются демо-данные и безопасные встроенные инструменты. Подключение к реальной инфраструктуре компаний — последующее расширение.

### Продуктовые принципы

- **Visual-first:** основной путь создания workflow — графический редактор, а не набор форм.
- **Debuggability-first:** любой запуск можно исследовать по узлам и событиям.
- **Trace over guesswork:** ошибки должны содержать этап, категорию, retryability и correlation IDs, а не только строку `Something went wrong`.
- **Reproducibility:** каждый запуск ссылается на неизменяемую версию workflow.
- **Safe by default:** узлы имеют явные схемы входов/выходов и ограниченные права.
- **Honest retries:** повтор шага доступен только там, где его семантика безопасна; внешние эффекты нельзя бездумно исполнять повторно.
- **Framework behind an adapter:** LangGraph/LangChain помогают исполнять graph/agent workflow, но не становятся публичным контрактом AgentDesk и не заменяют собственный trace/debugger.

## 2. Цели и критерии успеха

### Что должно получиться

К концу MVP пользователь должен уметь:

1. Создать workflow и собрать его в визуальном редакторе.
2. Добавлять узлы `Input`, `LLM`, `AI Agent`, `Tool`, `Condition` и `Output`, соединять их и редактировать настройки.
3. Получить ошибки валидации графа до запуска: отсутствующий вход, несовместимое соединение, недопустимый цикл, неизвестный тип узла или некорректная конфигурация.
4. Сохранить и опубликовать неизменяемую версию workflow.
5. Запустить workflow из UI или через API и следить за выполнением.
6. Смотреть на графе фактическое состояние каждого узла: queued/running/succeeded/failed/skipped/retrying.
7. Открывать подробную трассу узла: вход, выход, длительность, попытки, вызовы LLM/tool, ошибки, tokens и оценочная стоимость.
8. Понять причину падения по структурированной диагностике и связанным событиям.
9. Повторить весь запуск; для поддерживаемых безопасных узлов — повторить узел с зафиксированным входом.
10. Ограничивать время исполнения, количество шагов/итераций и бюджет.

### Критерии успеха MVP

- Workflow сохраняется как версионируемый граф, и запуски всегда привязаны к конкретной версии.
- Невалидный граф нельзя опубликовать или запустить.
- Каждый узел, каждая попытка и каждый значимый вызов внешней системы оставляют трассируемую запись.
- При ошибке интерфейс указывает точный узел, этап и классифицированную причину; внутренний traceback доступен в диагностике разработчика, но не выдаётся как небезопасный публичный ответ.
- Входы/выходы и логи имеют редактирование секретов и ограничение размера.
- API создания запуска быстро возвращает `202 Accepted`; выполнение идёт в worker.
- Повторная доставка задания не создаёт второй независимый запуск.
- Зависший запуск обнаруживается и завершается либо восстанавливается контролируемым механизмом.
- UI позволяет изучить неудачный запуск без подключения debugger к процессу и без поиска по разрозненным логам.
- Проект поднимается по инструкции через Docker Compose.

### Метрики продуктового качества отладки

На MVP не нужна сложная аналитика, но должны быть проверяемые критерии:

- для каждого выполненного узла доступны status, input/output snapshot и duration;
- у неуспешного узла доступны error category, safe message, retryability и trace/event ID;
- для LLM-вызова доступны provider, model, latency, usage и оценка стоимости, если данные доступны;
- разработчик может перейти с узла на связанный набор событий и увидеть хронологию;
- можно сравнить два запуска одной версии workflow по статусам узлов, длительности и результатам.

## 3. Что входит в MVP, а что нет

### Входит

- Простой аккаунт/локальная авторизация и владение workflow.
- Визуальный редактор на React Flow (`@xyflow/react`) с сохранением схемы.
- Базовые узлы: `Input`, `LLM`, `AI Agent`, `Tool`, `Condition`, `Output`.
- Валидация графа перед публикацией: обязательные узлы, соединения, конфигурация и запрет циклов в первой версии.
- Черновики и неизменяемые опубликованные версии workflow.
- Унифицированный интерфейс LLM-провайдера; минимум один реальный провайдер плюс fake provider для тестов.
- Реестр встроенных инструментов с JSON Schema и ограничениями.
- Runtime-адаптер на базе LangGraph для исполнения валидированного графа и ветвления `Condition`; собственная модель трассировки поверх событий runtime.
- Фоновые запуски через RabbitMQ и отдельный worker.
- Данные `Execution`, `NodeRun` и `TraceEvent` в PostgreSQL.
- Отладчик запуска: граф с наложенным статусом, timeline, вход/выход узла, ошибки, retries, usage и стоимость.
- Повтор всего запуска и безопасный повтор отдельных узлов с сохранённым input там, где узел объявлен повторяемым.
- Отмена, лимиты времени/итераций/размера данных и базовый budget guard.
- Структурированные логи, correlation IDs, тесты и демо-workflow.

### Не входит в первую версию

- Произвольный Python, shell и пользовательский код внутри узлов.
- Циклы и произвольные обратные рёбра на уровне графа. Внутренний цикл `AI Agent` ограничен собственным `max_iterations`.
- Мультиагентные команды и распределённая оркестрация нескольких графов.
- Полноценный RAG-конструктор с ingestion pipeline и внешним vector database. Архитектура должна предусматривать порты для embeddings/retrieval, но сам RAG и Qdrant подключаются после готовности базового Debugger.
- Подключение произвольных пользовательских credentials через UI и секретное хранилище enterprise-класса.
- Автоматическое восстановление любого внешнего побочного эффекта с гарантией exactly-once.
- Командные пространства, сложная RBAC, SaaS-биллинг и маркетплейс узлов.
- Масштабирование на Kubernetes.
- Продвинутый визуальный diff графов и совместное редактирование в реальном времени.

Важный компромисс: MVP уже включает визуальный редактор и полноценную базовую отладку, но ограничивает число типов узлов и способы ветвления. Это позволяет сделать законченный продукт, а не бесконечный универсальный редактор.

## 4. Предлагаемый стек

| Область | Технология | Для чего |
|---|---|---|
| API | FastAPI, Pydantic | REST API и валидация входных данных |
| Язык | Python 3.12+ | Основная реализация |
| База данных | PostgreSQL | Workflow, версии, запуски узлов и трассировки |

| Очередь | RabbitMQ | Доставка задач worker-процессам |
| Worker | Отдельный Python-процесс | Выполнение запусков вне HTTP-запроса |
| Кэш и лимиты | Redis — после базового запуска | Rate limiting, временные ключи и координация |
| AI runtime | LangGraph | Компиляция валидированного графа в исполняемый граф; состояние и checkpointing для поддерживаемых сценариев |
| LLM и стандартные AI-интеграции | LangChain там, где полезно | Chat model adapters, общие интерфейсы моделей/инструментов и, позже, embeddings/document loaders |
| AI | SDK провайдеров за адаптерами LangChain/AgentDesk | Генерация ответов; сохранять возможность подключить провайдера напрямую, если адаптер даёт больше контроля |
| Vector DB (после MVP) | Qdrant | Векторы фрагментов документов, метаданные и retrieval для RAG |
| Тесты | pytest, pytest-asyncio, httpx | Unit, integration и API-тесты |
| Нагрузочные тесты | Locust или k6 | Проверка API и сценариев конкуренции |
| Frontend | React, TypeScript, Vite | SPA редактора workflow и страницы отладки |
| Визуальный граф | `@xyflow/react` (React Flow) | Узлы, рёбра, кастомные панели конфигурации и overlay трассы |
| Состояние UI | Zustand или локальное состояние React | Выбор узла, selection, состояние canvas; не источник бизнес-истины |
| Наблюдаемость | structlog/стандартный logging + Prometheus | Логи, метрики и диагностика |
| Локальное окружение | Docker Compose | Frontend, API, worker, PostgreSQL, RabbitMQ и при необходимости Redis |

**Решение для AgentDesk:** не писать собственный графовый runtime с нуля. Хранить граф в собственном versioned JSON-контракте, валидировать его кодом AgentDesk, затем компилировать опубликованное определение через `LangGraphWorkflowRuntime`. LangChain использовать для интеграций с моделями/инструментами там, где он сокращает boilerplate. Важные границы: собственный формат workflow, API, модели трассировки и UI не должны зависеть от LangChain/LangGraph-типов.

Не нужно подключать одновременно все библиотеки экосистемы. Начать с LangGraph + одной интеграции Chat Model; дополнительные LangChain-компоненты использовать по мере необходимости. LangSmith не является обязательной runtime-зависимостью и не заменяет собственный Debugger.

## 5. Базовые понятия и модель исполнения

### Workflow и версия workflow

`Workflow` — именованный документ пользователя, который содержит визуальный граф. `WorkflowVersion` — неизменяемый опубликованный снимок графа. Редактирование меняет черновик; публикация создаёт новую версию. Уже запущенный workflow продолжает использовать ту версию, с которой он стартовал.

Версия хранится как JSONB-документ определения графа. Это сохраняет простую модель данных на MVP. Формат HTTP-запроса проверяется Pydantic-схемами в presentation; после mapping в application DTO отдельный Graph Validator проверяет семантику графа и конфигурации. Application не должен импортировать Pydantic API-схемы.

Пример упрощённого определения:

```json
{
  "schema_version": 1,
  "nodes": [
    {"id": "start_1", "type": "input", "config": {"fields": [{"name": "question", "type": "string"}]}},
    {"id": "llm_1", "type": "llm", "config": {"model": "configured-model", "prompt": "Answer the question"}},
    {"id": "end_1", "type": "output", "config": {"mapping": {"answer": "llm_1.text"}}}
  ],
  "edges": [
    {"id": "edge_1", "source": "start_1", "sourceHandle": "data", "target": "llm_1", "targetHandle": "input"},
    {"id": "edge_2", "source": "llm_1", "sourceHandle": "result", "target": "end_1", "targetHandle": "input"}
  ]
}
```

Пример иллюстративный: окончательный контракт узлов должен быть типизирован, иметь миграцию `schema_version` и не принимать произвольные поля без валидации.

### MVP-типы узлов

- `Input` — начальные данные и их схема.
- `LLM` — один вызов модели с промптом и, по возможности, структурированным output schema.
- `AI Agent` — ограниченный цикл model/tool calling с allowlist инструментов и лимитом итераций.
- `Tool` — вызов одного встроенного зарегистрированного инструмента.
- `Condition` — детерминированная проверка результата и выбор одной из исходящих веток.
- `Output` — формирование итогового результата workflow.

На MVP разрешён ориентированный ациклический граф (DAG). `Condition` может направлять выполнение по одной из веток, но произвольные циклы графа запрещены. Внутренний цикл `AI Agent` — отдельный runtime-механизм с жёстким лимитом.

**Как это реализовать без написания своего LangGraph-клона:** хранить AgentDesk JSON как публичное определение workflow; compile-ить его в LangGraph только на этапе запуска/кэширования runtime-графа. `LLM`-узел использует выбранный chat model adapter, `Tool` вызывает только зарегистрированные серверные инструменты, `Condition` компилируется в условный переход. Любая функция узла оборачивается trace-инструментированием AgentDesk. Внешний вид и формат трассы не должны меняться из-за того, какой provider/framework исполняет узел.

### Узел и его входы/выходы

Каждый тип узла задаёт:

- JSON Schema конфигурации;
- именованные входные/выходные порты;
- способ разрешения входных данных из результатов предыдущих узлов;
- executor;
- ограничения времени и размера результата;
- правила retry и idempotency;
- правила редактирования чувствительных полей в trace.

Graph Validator проверяет существование узлов и рёбер, уникальность ID, совместимость портов, наличие достижимого `Input` и `Output`, корректность конфигурации и отсутствие циклов. Проверка выполняется на backend; фронтенд может показывать ошибки раньше, но не заменяет серверную валидацию.

### Execution

`Execution` — конкретный запуск конкретной версии workflow. Он имеет идентификатор, input, output, статус, временные метки, лимиты и итоговую диагностику.

Состояния запуска: `queued`, `running`, `cancel_requested`, `succeeded`, `failed`, `cancelled`.

### NodeRun

`NodeRun` — одна попытка выполнения конкретного узла в рамках execution. Для каждой попытки сохраняются snapshot входа, output или error, timestamps, duration, статус и счётчик попытки. `NodeRun` имеет стабильный `node_id` из определения графа, чтобы UI мог подсветить соответствующий визуальный узел.

Состояния узла: `pending`, `running`, `succeeded`, `failed`, `skipped`, `retrying`, `cancelled`.

### TraceEvent

`TraceEvent` — хронологическое событие, связанное с запуском и, по возможности, с конкретным NodeRun. Примеры: `node.started`, `llm.request`, `llm.response`, `tool.started`, `tool.completed`, `retry.scheduled`, `node.failed`, `execution.cancel_requested`.

TraceEvent дополняет итоговое состояние узла, а не заменяет его. Это позволяет показать timeline и понять, например, упал ли узел во время сериализации входа, запроса к провайдеру или исполнения инструмента.

### Политика хранения входов и выходов

Сохранять диагностические snapshots полезно, но они могут содержать персональные данные или секреты. Перед записью применяется redaction по полям и лимит размера. Для каждого узла должен быть понятный режим хранения: обычный JSON, маскированный JSON или только метаданные. Скрытие данных в UI само по себе не считается защитой.

### Ответственность слоёв: простая слоёная архитектура и анемичная модель

Использовать **слоёную архитектуру с анемичными доменными моделями**. Для этого проекта не нужны тяжёлый DDD, агрегаты на каждый объект, доменные события или сложная иерархия базовых классов. Доменные модели преимущественно хранят состояние и типы данных; сценарии и бизнес-правила размещаются в application use cases/services и небольших policy/validator-компонентах.

- **Presentation:** FastAPI routes, Pydantic-схемы HTTP/API, проверка формы запроса, аутентификация и mapping API DTO в application DTO. Только здесь публичный HTTP-контракт знает о `Request`, `Response` и `HTTPException`.
- **Application:** use cases/handlers, orchestration, транзакционные границы, авторизация доступа к ресурсам, валидация workflow, правила retry/публикации и orchestration runtime. Команды, query/result DTO и контракты use case — простые `dataclass`/типизированные структуры; application не принимает Pydantic-модели API.
- **Domain:** анемичные `dataclass`-модели/типы, enum-состояния и идентификаторы (`Workflow`, `WorkflowVersion`, `Execution`, `NodeRun`, `TraceEvent`). Они не импортируют FastAPI, Pydantic API-схемы, SQLAlchemy, LangChain или LangGraph. Простые допустимые переходы можно описывать enum/validator/policy, не превращая модели в объекты с богатым поведением.
- **Infrastructure:** SQLAlchemy ORM-модели и мапперы, реализации repository-портов, RabbitMQ/Outbox, Redis, LLM adapter, `LangGraphWorkflowRuntime`, провайдеры embeddings и (после MVP) `QdrantVectorStore`. ORM-модели не выходят за границы инфраструктурных репозиториев.

Зависимости направлены внутрь: `presentation -> application -> domain/contracts`; инфраструктура реализует интерфейсы, объявленные для application. Не создавать абстракцию для каждого класса: вводить ports/interfaces на настоящих границах заменяемости, тестирования или внешних систем. В application-слой не должны протекать `Request`, `Response`, `HTTPException`, Pydantic-модели API, ORM-модели или типы LangChain/LangGraph.

### Главный поток запуска

```text
Client
  -> POST /executions
  -> проверка доступа и лимитов
  -> фиксация Execution в PostgreSQL
  -> фиксация события в Outbox
  -> ответ 202 Accepted с execution_id
  -> Outbox publisher публикует сообщение в RabbitMQ
  -> worker получает execution_id
  -> атомарно захватывает запуск
  -> LangGraphWorkflowRuntime компилирует опубликованное определение и исполняет граф
  -> адаптер AgentDesk нормализует события runtime в NodeRun и TraceEvent
  -> NodeRun и TraceEvent сохраняются в PostgreSQL
  -> GET /executions/{id} и /trace показывают прогресс, timeline и результат
```

Outbox нужен для устранения окна сбоя между сохранением запуска в БД и публикацией задания в очередь. Сама доставка сообщения может быть повторной, поэтому обработчик обязан быть идемпотентным.

### AI framework adapters и границы ответственности

**Workflow definition AgentDesk — источник истины.** Определение графа хранится в версионируемом JSONB-формате AgentDesk; не сохранять сериализованные объекты LangGraph/LangChain вместо собственного контракта. На запуске `LangGraphWorkflowRuntime` строит runtime-граф из уже провалидированного snapshot. Каждому visual `node_id` соответствует стабильный runtime wrapper, который пишет `node.started`, `node.completed` или `node.failed`, безопасные input/output snapshots, длительность и usage. События внутренних tool calls/итераций Agent можно записывать как вложенные `TraceEvent` с `parent_event_id`.

Рекомендуемые порты application-слоя:

- `IWorkflowRuntime` — запустить валидированную версию workflow и передать события/результат; инфраструктурная реализация — `LangGraphWorkflowRuntime`.
- `ILLMProvider` или более узкий `IChatModel` — интерфейс для use cases; реализация может использовать LangChain chat model или официальный SDK провайдера.
- `IToolRegistry` — получить разрешённый инструмент и его контракт; runtime не должен выполнять произвольный код, пришедший от пользователя/LLM.
- `IEmbeddingProvider` и `IVectorStore`/`IRetriever` — предусмотреть как точки расширения для будущего RAG, но не реализовывать Qdrant в MVP.

LangGraph может дать streaming событий и checkpointing состояния, но эти механизмы не заменяют бизнес-записи AgentDesk. Собственный `Execution` остаётся каноническим состоянием продукта, `NodeRun`/`TraceEvent` — пользовательским форматом диагностики. При падении runtime адаптер должен отмечать `trace_status=partial` и сохранять диагностическую информацию о восстановлении, если это можно определить, а не гарантировать наличие события завершения. Checkpointing LangGraph можно включить для восстановления состояния, сохраняя корреляцию с `execution_id` и `workflow_version_id`. Тестировать следует и компиляцию графа, и отображение runtime-событий в собственный trace.

## 7. Основные сущности БД

Для MVP лучше хранить граф опубликованной версии как валидированный JSONB snapshot, а результаты фактического исполнения — нормализованно. Это упрощает версионирование схемы и отладку отдельных узлов.

### `users`

Владелец workflow и запусков. Для локального MVP допускается простая авторизация. Секреты и пароли не хранить открытым текстом.

### `workflows`

- `id` — UUID;
- `owner_id`;
- `name`, `description`;
- `status` — active/archived;
- `draft_definition` — JSONB текущего черновика;
- `current_version_id` — nullable;
- `created_at`, `updated_at`.

### `workflow_versions`

- `id`, `workflow_id`, `version_number`;
- `definition` — неизменяемый JSONB snapshot узлов и рёбер;
- `schema_version` — версия формата определения графа;
- `created_by`, `created_at`, `published_at`;
- `definition_hash` — опционально, для идентификации одинаковых определений.

Уникальность: `(workflow_id, version_number)`. После публикации `definition` не изменяется.

### `tool_definitions`

Каталог доступных инструментов:

- `id`, `name`, `description`;
- `input_schema`, `output_schema` — JSON Schema;
- `risk_level`, `is_idempotent`, `is_retryable`;
- `default_timeout_ms`, `max_output_bytes`;
- `implementation_version`, `enabled`.

Реализация инструмента остаётся в коде приложения. Не разрешать пользователям передавать исполняемый Python-код.

### `executions`

- `id`, `owner_id`, `workflow_id`, `workflow_version_id`;
- `status`, `input_data`, `output_data`;
- `error_code`, `error_message` — безопасное краткое резюме ошибки;
- `idempotency_key`, `attempt_count`, `parent_execution_id`;
- `queued_at`, `started_at`, `finished_at`, `created_at`, `updated_at`;
- `total_input_tokens`, `total_output_tokens`, `estimated_cost`;
- `trace_status` — optional marker для выявления неполной трассы при сбое.

Клиентский ключ идемпотентности должен быть уникален в пределах владельца и endpoint-сценария.

### `node_runs`

Каждая попытка выполнения графового узла:

- `id`, `execution_id`, `node_id`, `node_type`;
- `attempt_number`, `status`;
- `input_snapshot`, `output_snapshot` — JSONB после redaction и ограничения размера;
- `error_category`, `error_code`, `safe_error_message`, `retryable`;
- `provider`, `model`, `input_tokens`, `output_tokens`, `estimated_cost` — nullable;
- `started_at`, `finished_at`, `duration_ms`;
- `replayed_from_node_run_id` — nullable, если запуск шага был повтором;
- `created_at`.

Уникальность: `(execution_id, node_id, attempt_number)`. Внутренние итерации узла `AI Agent` и его tool calls в MVP записываются как вложенные `TraceEvent`, а не как повторные графовые `NodeRun`. Повтор узла создаёт новое значение `attempt_number`.

### `trace_events`

- `id`, `execution_id`, `node_run_id` — nullable;
- `parent_event_id` — nullable, для вложенных событий agent/tool trace;
- `sequence_number`, `event_type`, `severity`, `iteration_number` — nullable;
- `message` — короткое читаемое описание;
- `payload` — структурированные метаданные JSONB после redaction;
- `occurred_at`.

Уникальность `(execution_id, sequence_number)`. В trace не записывать секреты, ключи провайдера и полные чувствительные данные без необходимости.

### `outbox_events`

- `id`, `event_type`, `aggregate_id`, `payload`;
- `created_at`, `published_at`;
- `attempt_count`, `last_error`.

Outbox закрывает окно сбоя между commit в PostgreSQL и публикацией запуска в RabbitMQ. Повторная публикация ожидаема, потребитель идемпотентен.

### `provider_usage` (можно отложить, если достаточно данных в `node_runs`)

Запись об использовании LLM: provider, model, execution/node run, latency, tokens, оценочная стоимость и статус. Не дублировать данные без понятной причины; на MVP можно хранить usage непосредственно в `node_runs` и агрегировать для UI.

## 8. Контракты API

Все маршруты располагаются под `/api/v1`. Ниже — функциональные контракты, точные Pydantic-схемы уточняются при реализации.

### Workflow и версии

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/workflows` | Создать workflow с пустым черновиком |
| `GET` | `/workflows` | Список доступных владельцу workflow |
| `GET` | `/workflows/{workflow_id}` | Получить метаданные и черновик |
| `PATCH` | `/workflows/{workflow_id}` | Изменить имя/описание/статус |
| `PUT` | `/workflows/{workflow_id}/draft` | Сохранить черновик графа |

| `GET` | `/workflows/{workflow_id}/versions/{version_id}` | Получить конкретный snapshot |

Ошибки Graph Validator должны включать `code`, `message`, `node_id` и/или `edge_id`, а также поле/порт, если применимо. Фронтенд использует эти данные, чтобы выделить проблемный узел прямо на canvas.

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/node-types` | Каталог типов узлов и схем конфигурации/портов |
| `GET` | `/tools` | Список инструментов платформы |
| `GET` | `/tools/{tool_name}` | Описание, schema, ограничения и retry policy инструмента |

### Запуски и отладка

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/workflows/{workflow_id}/executions` | Создать запуск опубликованной версии; `202 Accepted` |
| `GET` | `/executions/{execution_id}` | Состояние, итоговый output и метаданные |
| `GET` | `/executions/{execution_id}/graph` | Snapshot графа, к которому привязан запуск |
| `GET` | `/executions/{execution_id}/nodes` | Все NodeRun по узлам/попыткам |
| `GET` | `/executions/{execution_id}/nodes/{node_run_id}` | Подробности узла, input/output, ошибка и usage |
| `GET` | `/executions/{execution_id}/trace` | Хронология TraceEvent с фильтрами и пагинацией |
| `POST` | `/executions/{execution_id}/retry` | Создать новый полный запуск на основе того же input/version |

На MVP не выполнять downstream-узлы автоматически после node retry, если такой режим не реализован и явно не показан в UI.

### Правила API

- Единый формат ошибок: `code`, безопасный `message`, `request_id`, optional `details`.
- Проверять владение workflow и execution на каждом запросе.
- Не возвращать сырой traceback в обычном API-ответе; подробности доступны в ограниченной диагностической панели с очищенными данными.
- Валидировать схему и лимиты до помещения в очередь.
- Поддерживать `Idempotency-Key` при создании execution.
- Для долгих операций возвращать ID запуска, а не держать HTTP-соединение.
- Trace API поддерживает пагинацию и фильтры по `node_id`, `severity`, `event_type`.
- Не обещать мгновенную консистентность UI: статус и события могут появляться с небольшой задержкой.

## 9. Runtime и отладка исполнения

`LangGraphWorkflowRuntime` исполняет опубликованный снимок workflow через LangGraph, а адаптер AgentDesk формирует собственную подробную трассу. Application вызывает порт `IWorkflowRuntime`; реализации LangGraph и LangChain находятся в infrastructure и не должны протекать в application-контракты. Runtime не зависит от FastAPI, React, RabbitMQ или ORM напрямую. Очередь/worker и PostgreSQL-репозитории окружают runtime, а не встраиваются в функции узлов.

### Алгоритм запуска

1. Загрузить `Execution` и неизменяемый `WorkflowVersion`.
2. Атомарно захватить запуск и проверить, что он ещё не был завершён/захвачен другим worker.
3. Передать неизменяемое определение в `LangGraphWorkflowRuntime`, сопоставить каждому `node_id` функцию-обёртку и скомпилировать граф. В первой версии поддерживать только DAG и условные переходы `Condition`.
4. Инициализировать runtime state входными данными и записать `execution.started`.
5. LangGraph выбирает следующий узел по скомпилированному графу и результатам conditional edges; application не реализует второй scheduler.
6. Функция-обёртка узла создаёт `NodeRun`, пишет `node.started` и безопасный snapshot входа.
7. Функция-обёртка передаёт управление в соответствующий node executor с timeout и политикой retry.
8. По завершении функции-обёртки сохранить output, usage, duration и `node.completed`; пропущенные из-за `Condition` узлы явно отметить как `skipped`. События LangGraph сопоставлять с visual node IDs и нормализовать, не отдавая сырые внутренние события в публичный API.
9. При ошибке сохранить category/code/safe message, correlation IDs и доступную техническую диагностику, затем перевести execution в `failed` или запланировать ограниченный retry.
10. Дождаться завершения графа, отмены, ошибки или достижения лимита.
11. Зафиксировать финальный результат и состояние execution.

### Контракт executor узла

Каждый executor получает `NodeContext`, содержащий `execution_id`, `workflow_version_id`, `node_id`, входные данные, настройки лимитов и интерфейсы для trace/usage. Возвращает типизированный output либо поднимает нормализованную ошибку, например:

- `ConfigurationError` — неправильная конфигурация, не повторять;
- `InputValidationError` — вход не соответствует контракту;
- `ProviderRateLimitError` — можно повторить с backoff;
- `ProviderUnavailableError` — временная ошибка;
- `ToolTimeoutError` — инструмент превысил timeout;
- `ToolPermissionDeniedError` — вызов запрещён, не повторять;
- `BudgetExceededError` — выполнение остановлено лимитом;
- `CancelledError` — отмена пользователя.

Сырые exception и traceback сохраняются только в защищённой диагностике после очистки секретов. В публичный trace выводится нормализованная ошибка.

### Что должен видеть пользователь при падении

Для каждого упавшего узла debugger показывает:

1. **Где упало:** название узла, тип, ID и попытка.
2. **На каком этапе:** подготовка входа, вызов LLM, парсинг ответа, вызов инструмента, валидация результата или сохранение состояния.
3. **Почему:** категория ошибки, короткое объяснение, retryability и идентификатор связанного события.
4. **С чем работало:** отредактированный input snapshot и, если доступен, ответ внешнего провайдера/инструмента.
5. **Сколько стоило:** длительность, provider/model, tokens и оценка стоимости.
6. **Что делать дальше:** исправить конфигурацию, изменить input, посмотреть лог события, повторить узел (если разрешено) или перезапустить весь workflow.

Ошибки валидации графа возникают до запуска и подсвечиваются на canvas. Runtime-ошибки появляются на графе как failed node и раскрываются в панели диагностики.

### Retry и replay

Retry — не магическое восстановление любого действия. Для каждого `Tool` задаются `is_retryable` и `is_idempotent`. На MVP безопасный retry узла разрешён для чистых LLM-вызовов и инструментов, явно объявленных идемпотентными/read-only. Узлы с внешним побочным эффектом не повторяются автоматически.

Повтор узла использует сохранённый input snapshot и создаёт новую попытку. Он не меняет старую трассу. Повтор downstream-ветки с checkpointing можно добавить позже: он требует аккуратного определения, какие результаты можно использовать повторно и не создаст ли запуск дублирующий внешний эффект.

### Инварианты исполнения

- Запуск привязан к точному version snapshot workflow.
- Один NodeRun относится к конкретной попытке конкретного узла; старые попытки не перезаписываются.
- У каждого значимого runtime-события есть `execution_id`, а у событий узла также `node_run_id`/`node_id`.
- Неуспешный узел должен оставить диагностическое событие, даже если ошибка возникла до выполнения кода узла.
- Retry, отмена и повторная доставка не должны стирать trace.
- Число итераций AI Agent, время запуска, размер данных и бюджет ограничиваются сервером.
- Вызвать можно только узел/инструмент, разрешённый опубликованной версией и backend-политикой.
- Граф MVP — DAG; `Condition` выбирает одну ветку, а не запускает все одновременно.
- События и snapshots очищаются от секретов до сохранения.

## 10. Безопасность и ограничения

AI-агент потенциально обрабатывает недоверенный ввод и может ошибочно выбирать действия. Безопасность должна быть частью контракта инструмента, а не только текстом system prompt.

Минимальные правила:

1. Не передавать ключи провайдеров модели в контекст LLM и в логи.
2. Не выполнять код, который вернула модель.
3. По умолчанию использовать read-only инструменты.
4. Ограничивать время каждого вызова инструмента, размер ответа и общий размер контекста.
5. Проверять JSON-аргументы по schema и применять бизнес-валидацию после schema validation.
6. Если инструмент делает HTTP-запрос, не допускать произвольный доступ к localhost, private IP, metadata endpoints и внутренним сетям; предпочтительнее allowlist разрешённых хостов. Учитывать редиректы и DNS rebinding.
7. Ограничивать количество запросов к LLM и число параллельных запусков на пользователя.
8. Не считать инструкции в найденных документах или логах доверенными системными инструкциями. Эти данные могут содержать prompt injection.
9. Удалять секреты и чувствительные данные из логов и сохранённых результатов, где это возможно.
10. Все ограничения проверять на backend, независимо от состояния UI.

Для MVP полезнее иметь 3 безопасных инструмента, чем 20 мощных инструментов без изоляции и ограничений.

- React + TypeScript + Vite и базовую оболочку интерфейса;
- `/health/live` и `/health/ready`.

**Готово, когда:** приложение и frontend запускаются локально, миграции применяются на чистой БД, CI проходит. Не делать Kubernetes, микросервисы или сложную систему авторизации.

### Этап 1. Workflow, черновики и версии

**Задача:** определить контракт workflow как версионируемого графа.

Сделать:

- модели `Workflow`, `WorkflowVersion` и typed-схемы `NodeDefinition`, `EdgeDefinition`;
- хранение черновика графа в JSONB;
- create/list/get/update workflow;
- публикацию неизменяемой версии;
- `schema_version` и стратегию изменения формата графа;
- проверки владельца и unit/API-тесты.

**Критерии приёмки:** черновик можно менять; опубликованная версия не меняется; запуск в будущем сможет ссылаться на однозначную версию. Не добавлять ORM-модель на каждый визуальный узел/ребро без необходимости.

### Этап 2. Визуальный редактор графа

**Задача:** пользователь может создать схему без ручного редактирования JSON.

Сделать:

- React Flow canvas (`@xyflow/react`), перемещение узлов и соединение портов;
- панель добавления узлов `Input`, `LLM`, `AI Agent`, `Tool`, `Condition`, `Output`;
- правую панель конфигурации выбранного узла;
- сохранение черновика на backend;
- состояния dirty/saved/saving/error;
- отображение ошибок Graph Validator на соответствующих узлах/рёбрах;
- запрет публикации графа, который сервер признал невалидным.

**Критерии приёмки:** workflow можно построить, сохранить, перезагрузить страницу и продолжить редактирование; некорректные соединения нельзя опубликовать. Не делать совместное редактирование и сложные анимации.

### Этап 3. Graph Validator и контракты узлов

**Задача:** сделать граф безопасным и исполнимым до добавления очередей.

Сделать:

- каталог типов узлов и их JSON Schema;
- именованные input/output порты;
- проверку уникальности ID, существования концов ребра и совместимости портов;
- проверку достижимости входа и выхода, циклов и некорректных branch connections;
- конфигурационные схемы и проверку ограничений каждого узла;
- API `/node-types`, `/validate`, структурированные ошибки с `node_id`/`edge_id`.

**Критерии приёмки:** одинаковые определения графа дают одинаковый результат валидации; backend остаётся источником истины; ошибки можно однозначно отобразить на canvas.

### Этап 4. Исполнение узлов и базовый trace

**Задача:** исполнять реальный граф и сохранять трассу каждого узла.

Сделать:

- `Execution`, `NodeRun`, `TraceEvent` и миграции;
- `LangGraphWorkflowRuntime`, компиляция DAG из AgentDesk JSON и ветвление `Condition`;
- один fake LLM provider и один реальный provider adapter;
- инструменты `current_time`, `search_demo_logs` и `search_local_docs`;
- узлы `Input`, `LLM`, `Tool`, `Condition`, `Output`;
- ограниченный `AI Agent` node с allowlist инструментов и `max_iterations`;
- запись started/completed/failed events, input/output snapshots, duration и ошибок;
- нормализованные категории ошибок и redaction перед сохранением.

**Критерии приёмки:** демо-workflow выполняется от Input до Output; у каждого узла есть NodeRun и trace; искусственно сломанный узел подсвечивается по ID; unit-тесты не требуют платных запросов.

### Этап 5. Debugger UI — главное отличие продукта

**Задача:** превратить raw execution records в понятную отладку.

Сделать:

- страницу execution с snapshot графа именно той версии, что запускалась;
- overlay статуса узлов на графе: queued/running/succeeded/failed/skipped/retrying;
- список/timeline событий с временем и уровнем severity;
- инспектор узла: вход, выход, попытки, длительность, error category, safe message и связанные события;
- подробности LLM-вызова: provider/model, latency, tokens и estimated cost, если доступны;
- фильтры по узлу, типу события и severity;
- сравнение двух запусков по состояниям узлов, длительности и output;
- понятные empty/loading/partial-trace states;
- повтор полного запуска и UI для безопасного retry отдельного узла.

**Критерии приёмки:** при искусственной ошибке пользователь за несколько кликов находит упавший узел, видит вход и причину, понимает, можно ли повторять его. Если trace неполный из-за падения процесса, UI явно сообщает об этом, а не показывает ложное «всё завершено».

### Этап 6. Очередь, фоновое исполнение и восстановление

**Задача:** запуск не зависит от жизни HTTP-запроса и переживает типовые сбои.

Сделать:

- `POST /workflows/{id}/executions` возвращает `202 Accepted`;
- outbox publisher и очередь RabbitMQ;
- отдельный worker и идемпотентный захват execution;
- обработку повторной доставки;
- retry временных ошибок с ограниченным числом попыток/backoff;
- отмену и graceful shutdown;
- lease/heartbeat и обнаружение зависших запусков;
- отдельные trace events для retry, recovery и cancel.

**Критерии приёмки:** падение между commit в БД и публикацией не теряет запуск; повторная доставка не создаёт конкурентное повторное исполнение; после restart состояние восстанавливается или получает явную диагностическую ошибку.

### Этап 7. Лимиты, usage и эксплуатационная диагностика

**Задача:** контролировать потребление ресурсов и находить проблемы в самом backend.

Сделать:

- лимиты времени и числа итераций на запуск/AI Agent;
- лимит размера входа, output и snapshots;
- подсчёт tokens и примерной стоимости;
- ограничение активных запусков;
- структурированные backend logs с `request_id`, `execution_id`, `node_id`, `node_run_id`;
- метрики latency/ошибок по провайдерам и инструментам;
- маскирование секретов и конфигурируемую политику сохранения входов/выходов;
- базовый Prometheus endpoint и при желании Grafana dashboard.

**Критерии приёмки:** бюджет и лимиты проверяются backend; пользователь видит измеряемые данные без утечек секретов; можно отличить ошибку узла от проблемы инфраструктуры/worker.

### Этап 8. Тестирование и демонстрационный релиз

**Задача:** подготовить доказуемо работающий проект для портфолио.

Сделать:

- integration tests с PostgreSQL и RabbitMQ;
- fake providers и contract tests LLM adapter;
- contract/integration tests LangGraph adapter: compile, node ID mapping, trace mapping, conditional edges и восстановление checkpoint, если включено;
- тесты Graph Validator;
- сценарии падения на каждом важном этапе узла;
- тест повторной доставки и recovery;
- e2e создание workflow → публикация → запуск → debugger;
- нагрузочный тест API и ограничение параллелизма;
- README, схема архитектуры и ADR ключевых решений;
- готовый демо-workflow с инжектируемыми ошибками.

**Критерии приёмки:** чистая установка работает; тесты запускаются одной командой; демонстрация показывает как успешный запуск, так и несколько диагностируемых отказов; измерения реальные, не придуманные.

## 12. Минимальный тест-план

### Graph Validator

- пустой граф, отсутствующий Input или Output;
- duplicate node/edge IDs;
- edge с несуществующим node ID или port;
- цикл в графе;
- несовместимые типы портов;
- некорректная конфигурация узла;
- ветка Condition без корректного условия или направления;
- неизменность опубликованного workflow version.

### Runtime и trace

- линейный workflow Input → LLM → Output;
- workflow с Tool и последующим LLM;
- Condition запускает только одну выбранную ветку, другая помечается skipped;
- AI Agent прекращает цикл по финальному ответу или `max_iterations`;
- ошибка сериализации input создаёт диагностическое событие;
- ошибка LLM и ошибка инструмента дают разные категории;
- для каждого executed node существует NodeRun, для каждого retry — отдельная попытка;
- duration и tokens агрегируются согласованно;
- snapshot сохраняет маскированные данные и никогда не содержит секрет провайдера;
- два запуска одной версии можно сравнить, исходная трасса не изменяется.

### Интеграционные тесты

- сохранение/загрузка draft JSONB;
- публикация и чтение неизменяемой версии;
- сохранение execution/node_runs/trace_events;
- outbox publisher и RabbitMQ;
- два worker одновременно пытаются забрать один execution;
- duplicate delivery;
- recovery после падения worker;
- cancel во время ожидания ответа LLM;
- node retry проверяет `is_retryable`/`is_idempotent` и использует сохранённый input;
- пользователь не может читать чужой workflow/execution.

### Сценарии отладки и отказов

1. LLM отвечает `429` — UI отображает provider rate limit и retryability.
2. LLM недоступна — trace показывает node, этап, elapsed time и request/correlation ID.
3. LLM возвращает некорректный structured output — ошибка parsing/validation видна отдельно от transport error.
4. Tool превышает timeout — запуск завершается контролируемо, trace не теряется.
5. Tool возвращает слишком большой output — результат отклоняется/обрезается согласно политике, есть событие.
6. Условие уводит выполнение в другую ветку — узлы невыбранной ветки имеют статус skipped.
7. Worker падает до старта узла — recovery не создаёт двойной активный NodeRun.
8. Worker падает после внешнего вызова до записи результата — UI явно показывает interrupted/unknown outcome, а не утверждает, что внешнее действие не произошло.
9. Одно сообщение доставляется дважды — execution не исполняется параллельно двумя worker.
10. Достигнут лимит бюджета или итераций — error category ясна и видна в debugger.
11. Пользователь повторяет node, который не idempotent — API запрещает повтор.
12. Публикуется новая версия workflow во время старого запуска — старый запуск использует прежний snapshot.
13. Trace частично отсутствует из-за аварийного завершения — состояние partial trace явно показано.

**Отдельный acceptance test продукта:** дать человеку, который не писал workflow, намеренно сломанный демо-сценарий. Он должен по UI определить упавший узел, увидеть безопасный input, тип причины и понять следующий шаг без чтения source code. Это ключевой тест отличия AgentDesk.

## 13. Нефункциональные требования

### Надёжность

- PostgreSQL хранит каноническое состояние запусков.
- Сообщения очереди можно доставлять повторно.
- Все переходы состояний проверяются на сервере.
- Необработанная ошибка не должна оставлять execution в неопределённом состоянии без механизма восстановления.

### Производительность

В первой версии не задавать искусственную цель «10 000 RPS». Сначала измерить базовые показатели и зафиксировать условия эксперимента. Время ответа `POST execution` не должно зависеть от полного времени ответа LLM; endpoint только валидирует и ставит задачу на выполнение.

### Безопасность

- Секреты только через переменные окружения или секретное хранилище.
- Доступ к сущностям проверяется по владельцу.
- Логи ограничены и очищены от секретов.
- Инструменты запускаются с таймаутами и минимальными правами.

### Поддерживаемость

- Application-слой тестируется без реального LLM API.
- Репозитории и провайдеры подключаются через интерфейсы там, где это даёт реальную заменяемость.
- Сложные решения сопровождаются короткими ADR.
- Бизнес-логика не размещается в роутерах FastAPI.

## 14. Пример пользовательского сценария для демо

Демо должно показывать не только «счастливый путь», но и то, как AgentDesk помогает найти причину отказа.

### Успешный запуск

1. Создать workflow `Error Analyst`.
2. В редакторе собрать `Input → AI Agent → Output` и подключить к AI Agent инструменты `search_demo_logs`, `search_local_docs`, `current_time`.
3. Установить `max_iterations`, timeout и budget limit.
4. Сохранить draft, запустить серверную валидацию и опубликовать версию.
5. Запустить workflow из UI.
6. На canvas увидеть статус выполнения узлов; открыть AI Agent и посмотреть внутренние итерации, tool calls, вход/выход, длительность и usage.
7. Получить итоговый отчёт и стоимость запуска.

### Неуспешный запуск и отладка

1. В демо-конфигурации намеренно указать неправильное имя инструмента или заставить tool вернуть контролируемую ошибку.
2. Запустить workflow и увидеть failed node на canvas.
3. Открыть инспектор узла: безопасные входные данные, номер попытки, этап сбоя, error category, message, duration и связанное событие trace.
4. Исправить конфигурацию и опубликовать новую версию; исходный запуск и его трасса остаются неизменными.
5. Повторить весь запуск на новой версии и сравнить два результата.
6. Отдельно продемонстрировать безопасный retry read-only/idempotent узла с сохранённым input.
7. Выключить worker в тестовом сценарии и показать, что система либо восстанавливает запуск, либо явно отмечает interruption/partial trace.

В презентации проекта обязательно показать отладочный сценарий. Это важнее, чем большое количество типов узлов.

## 15. Что добавить после MVP

### Приоритет A — углубление отладки

- diff конфигурации workflow между версиями;
- diff входов/выходов одного и того же узла между запусками;
- replay workflow с checkpointing и продолжением от последнего безопасного узла;
- сравнение результатов LLM на нескольких провайдерах/моделях;
- экспорт trace в JSON/JSONL и OpenTelemetry;
- редактируемые политики retention и redaction;
- пользовательские annotations и заметки на узлах;
- trace sampling для очень частых/длинных запусков.

### Приоритет B — богатый редактор и новые узлы

- циклы/repeat и параллельные ветки с явными правилами join;
- HTTP Request node с SSRF-защитой и allowlist;
- преобразование данных (JSON mapping/template);
- human approval node;
- schedule/trigger nodes и webhooks;
- шаблоны workflow и версии пользовательских node packages;
- визуальные ссылки между подграфами.

### Приоритет C — knowledge/RAG и evaluation

- загрузка документов и асинхронная индексация;
- chunking, embeddings, retrieval с фильтрацией по владельцу/knowledge base;
- Qdrant adapter за `IVectorStore`/`IRetriever`;
- сначала инструмент `search_knowledge_base`, доступный из узла `AI Agent`, затем отдельный визуальный `RAG Retrieval` node с цитатами;
- hybrid search и reranking после измерения качества базового retrieval;
- evaluation-наборы для качества workflow;
- регрессионные тесты промптов/моделей и сравнение стоимости/latency.

#### План будущей RAG-интеграции с Qdrant

**RAG не входит в MVP, но границы нужно заложить сейчас.** Не связывать application use cases напрямую с SDK Qdrant. Реализовать инфраструктурный `QdrantVectorStore`, который удовлетворяет application-порту `IVectorStore`/`IRetriever`; embedding model подключать через `IEmbeddingProvider`. В конфигурации retrieval фиксировать provider/model embeddings, размерность и версию chunking, чтобы переиндексация была управляемой.

Предлагаемый поток индексации: загрузка документа -> запись метаданных в PostgreSQL -> задача индексации в worker -> извлечение текста -> chunking -> создание embeddings -> upsert в Qdrant -> обновление статуса документа. Повторная индексация должна быть идемпотентной по `document_id + document_version + chunk_index` или стабильному chunk ID; при удалении документа соответствующие точки в Qdrant также удаляются. Долгие операции выполняются в фоне, ошибки индексации видны пользователю.

Минимальные сущности PostgreSQL на будущий этап:

- `knowledge_bases`: владелец, название, настройки embeddings/chunking и статус;
- `documents`: `knowledge_base_id`, имя/тип/источник, `content_hash`, версия, status, ошибка индексации, timestamps;
- `document_chunks` (опционально): метаданные фрагментов и mapping на Qdrant point ID; не хранить дубли текста без причины. Исходные файлы и извлечённый текст могут позднее выноситься в object storage.

В payload Qdrant хранить метаданные для retrieval: `owner_id`/tenant, `knowledge_base_id`, `document_id`, `document_version`, `chunk_index`, source/title и, если принято решение, текст фрагмента. **Фильтр доступа по владельцу/knowledge base добавляется backend-ом всегда** и не может контролироваться инструкциями LLM. Создать payload indexes для часто используемых фильтров. Не полагаться на один только UI для изоляции документов.

План API на RAG-этап:

- `POST /knowledge-bases` и `GET /knowledge-bases`;
- `POST /knowledge-bases/{id}/documents` — загрузка/регистрация документа и постановка индексации в очередь;
- `GET /knowledge-bases/{id}/documents` и `GET /documents/{id}` — список, статус и диагностика;
- `POST /knowledge-bases/{id}/search` — диагностический retrieval endpoint для проверки результата поиска до использования в workflow.

В Debugger RAG/Tool trace должен показывать query, knowledge base, применённые фильтры (без секретов), число найденных фрагментов, scores, `document_id`/source, latency и ошибку embedding/vector DB. Необходимо ограничивать размер текстовых фрагментов в trace и предусмотреть redaction. MVP-проверка RAG: документ индексируется; поиск возвращает только фрагменты из разрешённой базы; агент может использовать `search_knowledge_base`; в ответе есть цитируемые источники; повторная индексация и удаление не оставляют устаревших векторов.

### Приоритет D — SaaS-возможности

- организации, команды и RBAC;
- безопасное хранение подключённых credentials;
- аудит действий;
- лимиты и биллинг;
- изоляция tenant-данных и отдельные политики хранения trace.

## 16. Решения, которые важно не переусложнять

- **Не откладывать визуальный редактор.** Он является частью ценности продукта и входит в MVP, но начни с шести простых типов узлов и ограниченного DAG.
- **Не пытаться поддержать все возможности Langflow.** Сфокусируйся на диагностике, воспроизводимости, trace и безопасном retry.
- **Не начинать с произвольного выполнения Python/shell.** Использовать контролируемый реестр инструментов.
- **Не разрешать произвольные циклы графа.** На MVP поддерживать DAG и ограниченный внутренний цикл AI Agent.
- **Не хранить каждый визуальный узел отдельной таблицей.** На старте definition версии в JSONB проще; run data хранить нормализованно.
- **Не использовать один большой log string вместо trace модели.** Нужны структурированные события с event type, severity, timestamp и ссылкой на node run.
- **Не раскрывать сырой traceback конечному пользователю.** Разделять safe error summary и защищённую диагностику, очищать секреты.
- **Не обещать exactly-once для внешних действий.** Повторять только идемпотентные операции или операции с idempotency key.
- **Не делать автоматический retry любой ошибки.** Сначала классифицировать ошибку и проверять retry policy узла.
- **Не использовать Redis как источник истины для execution.** Каноническое состояние — в PostgreSQL.
- **Не добавлять полноценный RAG, marketplace, billing и multi-agent orchestration до готовности debugger.** Сначала довести trace и LangGraph adapter до рабочего состояния; затем добавить Qdrant через отдельный vector-store порт. Основной дифференциатор — помочь быстро понять, почему workflow не сработал.
- **Не делать observability только для backend-разработчика платформы.** Пользовательский debugger должен использовать те же correlation IDs и события, что и системные логи, но показывать безопасную проекцию.

## 17. Архитектурные решения (ADR, кратко)

### ADR-001. Анемичные модели и application use cases

Принято: простая слоёная архитектура; доменные структуры — преимущественно `dataclass`/enum без инфраструктурных зависимостей; бизнес-правила находятся в application services/use cases и отдельных validators/policies. Repository интерфейсы определяются на границе application, SQLAlchemy ORM-модели и mapping находятся в infrastructure. API Pydantic DTO преобразуются в application DTO на presentation-границе. Это соответствует учебной цели и не требует тяжёлого DDD.

### ADR-002. LangGraph как implementation detail runtime

Принято: использовать LangGraph для исполнения опубликованного визуального графа и stateful agent-логики; LangChain — для интеграций моделей/инструментов там, где он сокращает ручную интеграцию. Собственный Graph Validator, versioned workflow JSON, execution records и normalized trace остаются в AgentDesk. `IWorkflowRuntime` изолирует runtime от use cases. Не строить второй полный graph scheduler без измеренной причины.

Риск: LangGraph runtime events/checkpoints не равны бизнес-трассе AgentDesk. Поэтому каждый visual node оборачивается адаптером, который пишет собственные `NodeRun`/`TraceEvent`; контрактные тесты фиксируют mapping visual node IDs, event types и статусов. Framework version pin и upgrade tests обязательны. LangSmith можно подключать как необязательный dev-инструмент, но Debugger не должен зависеть от него.

### ADR-003. Qdrant для RAG после MVP

Принято: Qdrant подключается только на отдельном этапе после отладки основного runtime. Application знает `IVectorStore`/`IRetriever` и `IEmbeddingProvider`, но не `qdrant_client`. PostgreSQL хранит метаданные knowledge base, документы и статусы индексации; Qdrant хранит vectors/payload и выполняет retrieval. Фильтрация по владельцу/knowledge base всегда формируется backend-ом.

## 18. Definition of Done для всего MVP

MVP можно считать завершённым, если выполнены все пункты:

- [ ] Проект поднимается локально одной командой по README.
- [ ] Пользователь создаёт workflow, собирает его в визуальном редакторе и сохраняет draft.
- [ ] Публикация создаёт неизменяемую версию; запуск использует точный snapshot.
- [ ] Graph Validator проверяет узлы, порты, конфигурации, графовые циклы и обязательные вход/выход.
- [ ] Работают узлы Input, LLM, AI Agent, Tool, Condition и Output в заявленных границах MVP.
- [ ] `LangGraphWorkflowRuntime` компилирует опубликованный AgentDesk-граф; runtime-статусы и события сопоставляются со стабильными `node_id` и собственной моделью trace.
- [ ] Application/domain-слои не зависят от FastAPI DTO, SQLAlchemy ORM-моделей и типов LangChain/LangGraph.
- [ ] Запуск выполняется асинхронно через worker и доступен по `execution_id`.
- [ ] Состояния execution, NodeRun и TraceEvent сохраняются в PostgreSQL.
- [ ] Canvas показывает фактический статус узлов для выбранного запуска.
- [ ] Успешный узел показывает безопасные input/output, длительность и доступный usage.
- [ ] Неуспешный узел показывает категорию причины, понятное сообщение, retryability и связанные trace events.
- [ ] Trace-данные очищаются от секретов и имеют ограничение размера.
- [ ] Полный retry создаёт новый execution; safe node retry не перезаписывает старую попытку.
- [ ] Повторная доставка RabbitMQ безопасна; Outbox закрывает риск потери задания между DB commit и публикацией.
- [ ] Реализованы лимиты времени, числа итераций и размера данных.
- [ ] Есть unit-, integration- и end-to-end тесты, включая специально сломанный workflow.
- [ ] Пройдён acceptance test: новый пользователь может понять причину демо-падения через UI без чтения кода.
- [ ] README описывает архитектуру, локальный запуск, trace model, границы retry и известные ограничения.
- [ ] В репозитории нет настоящих API-ключей и секретов.
